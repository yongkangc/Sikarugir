# Initial local baseline: 9 October 2026

Hardware: Apple M4 Max, 36 GB memory, macOS 15.7.3 (24G419), AC power, default
AC power mode. Other desktop applications remained running.

Installed wrapper: 1.0.21; Configure: 1.0.10; Wine Sikarugir: 11.0 revision 1;
DXMT version file: `v0.80-244-g7c8dee1`, whose version stamp maps to source commit
`7c8dee1c2d73415301ceb7d1fa810861cef4cd67`. The separately checked out DXMT source,
`e94c312f5c054263acf261cfa109edf13e757587`, is newer than the installed binary.

## Risk of Rain 2 menu

The game was launched and the user confirmed it was at the menu. Unity's current
Player.log reports Unity 2021.3.45f2 and Direct3D 11.0 feature level 11.1 on Apple
M4 Max. A live process sample identifies x86-64 execution translated through
Rosetta, with DXMT's `winemetal.so` loaded. Supporting D3DMetal and MoltenVK
libraries are also mapped; their presence alone does not establish which API
route is actively rendering a frame.

| Measurement | Result |
|---|---:|
| Resource intervals, no stack sampler running | 12 one-second intervals |
| Game process CPU, mean | 106.8% of one core |
| User / system CPU, mean | 46.1% / 60.7% |
| Maximum physical footprint | 4.81 GiB |
| Whole-device GPU utilization counters | 44–53% |

This is a menu baseline, not gameplay. Focus state, resolution, quality, VSync and
frame cap were not verified. Whole-device GPU counters include other applications.
These results cannot establish a CPU, GPU or Rosetta bottleneck, nor justify an
FPS improvement claim. Many Windows stack frames have no symbols and incomplete
unwinds, limiting function-level attribution.

Eight graphics pipeline errors were found in an older wrapper log last modified
at 16:26. The current launch started at 18:13, so those errors are excluded from
this baseline's causal evidence. The current game log confirms the graphics API.

The first resource-capture prototype omitted the Mach timebase conversion; its
output is marked invalid and excluded here. Corrected accounting was checked
against `time.process_time()` during a CPU workload and agreed with `top` in
separate live measurements. Four focused capture-tool tests passed. The log
collector also ran successfully, but there were no Metal HUD events in this
launch; frame times remain unmeasured.

## User-confirmed solo gameplay

After restarting the game and Windows Steam, the user confirmed active solo
gameplay. The capture measured 25 one-second resource intervals with Metal HUD
logging enabled; a five-second CPU stack sample ran afterward. The wrapper's
`METAL_HUD` setting was temporarily enabled for launch, then restored to its
original value of zero. Both Steam clients and the game were closed afterward.

Saved game settings were 1728×1080, resolution scale 1, fullscreen, VSync off,
120 FPS cap, all shadows and high shadow resolution. These are configuration-file
values, not independent confirmation of each active in-game setting. No controlled
resolution or backend comparison has been run.

| Measurement | Result |
|---|---:|
| Valid logged frames | 2,515 |
| Rate derived from logged presentation intervals | 100.15 FPS |
| Presentation interval, mean / median | 9.99 / 9.74 ms |
| Presentation interval, p95 / p99 / maximum | 14.28 / 16.67 / 31.77 ms |
| GPU duration, mean / p95 | 3.36 / 4.43 ms |
| Logged frames over 16.67 / 33.33 ms | 28 / 0 |
| Game process CPU, mean | 450.6%, equivalent to 4.51 cores |
| User / system CPU, mean | 184.6% / 266.0% |
| Maximum physical footprint | 5.08 GiB |
| Page-ins during resource capture | 1 |
| Whole-device GPU counter, mean | 39.72% |

Twenty-seven HUD messages contained two conflicting boundary frame markers. The
parser normally rejects conflicts; explicit exclusion removed both readings for
these two markers, less than 0.1% of the capture. Logging gaps are not reconstructed,
so the FPS value describes logged intervals rather than a separate wall-clock
frame counter. Payload interpretation follows
[Apple's Metal HUD presentation](https://developer.apple.com/videos/play/tech-talks/110339/).

GPU duration is substantially shorter than the presentation interval in this
capture. CPU submission, synchronization and pacing are therefore useful next
investigations. This does not establish a specific bottleneck: CPU totals do not
identify the critical thread, and subtracting GPU duration from presentation
interval does not measure CPU time. Rosetta/Windows stack unwinds are incomplete
and do not provide reliable function-level attribution. Metal HUD and shader-event
logging were enabled; their overhead has not been measured against an otherwise
identical uninstrumented run. Earlier menu results use a different scene and
instrumentation and are unsuitable as a before/after performance comparison.

The next comparison should hold the scene and launch conditions constant, use
frame-only logging, and test a lower resolution with the FPS cap removed. Then
compare graphics backends or Wine synchronization modes one at a time. A full
runtime rebuild requires additional build tools; no replacement has been installed.

## Small DXMT source candidate

The [HUD formatting patch](../patches/dxmt-hud-formatting.patch) skips
`UpdateStatistics` formatting when `DXMT_DEBUG` is absent. The original HUD sink
already discards these lines in that build mode, but its callers still create the
formatted strings. The patch preserves initialization, command submission, frame
latency and the debug HUD path.

An isolated x86-64 probe compiled the actual method and production statistics
headers against a substitute HUD sink. Across ten alternating before/after
passes, median cost was 0.938 microseconds before and 0.00139 microseconds after.
All 27 debug cases produced identical text, including compatibility flags and
spatial/temporal scaler labels. The older local libc++ needed experimental format
support with exceptions disabled for valid fixture inputs. Its formatting costs
are not those of the Windows DXMT binary. This is a small cleanup, far below the
roughly 10 ms frame interval; it does not explain the observed CPU usage or
demonstrate improved gameplay. The patch has not been built into a full DXMT engine.

## Completed configurator source improvement

The [reviewable patch](../patches/configurator-performance.patch) is based on
public Configure revision `4be1b048f8df14b073a6e39e8245bbb52c6a71c0` (version 1.0.4).
It fixes process-helper deadlocks/nonwaiting behavior, streams executable scans,
uses set membership for snapshot differences, and caches Winetricks child ordering.

The Winetricks probe compiles the actual source callbacks and filter. Its
synthetic fixture contains 1,000 packages across six uneven categories. Means of
ten passes, with before/after execution order alternated:

| Enumerate all child rows | Original | Patched |
|---|---:|---:|
| After list replacement, including first sort | 93.81 ms | 0.725 ms |
| Repeated enumeration of the same list | 94.08 ms | 0.427 ms |

Five-second CPU samples identified repeated string comparison and sorting in the
original callback. Those sorting functions disappeared from the patched steady
state's dominant samples. Cache resets preserve sorted order, package identity,
name/description filtering, empty results and same-instance refresh behavior.
Busy/view guards, leaf handling and index bounds were exercised as well.

Six process-helper checks and extracted executable-difference checks passed;
both modified Objective-C implementation files passed compiler syntax checks and
the complete patch passed reverse-apply and whitespace checks. A full GUI build
requires Xcode and has not been performed. The installed configurator is newer
than the public source and has not been replaced. These improvements concern the
configuration interface; they provide no demonstrated game FPS gain.
